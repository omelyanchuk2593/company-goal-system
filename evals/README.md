# Проверка скилла

Дата первого прогона: 30 октября 2026 года. Все задачи и данные компаний
синтетические. Это проверка поведения ассистента и инструментов, а не
измерение эффекта внедрения в реальной компании.

## Как проверяли

До создания скилла отдельный агент ответил на сценарий внедрения без методических
инструкций. После сборки два агента с чистым контекстом получили скилл и по два
сценария, без доступа к baseline и ожиданиям. Затем каждый оценил ответы другого
агента по заранее записанным критериям. Автор пакета просмотрел ответы отдельно.
Это один прогон каждого сценария, без статистической оценки устойчивости.

| Сценарий | Что проверяет | Ответ | Оценка |
|---|---|---|---|
| 1. Запуск компании | Первый результат без выдуманных данных, пять корзин, роли, непрерывные сроки | [Ответ 1](results/1.md) | [Критерии](results/1.grading.json) |
| 2. Шестая цель и 2★ | Ограничение ёмкости, честное согласование и доработка формулировки | [Ответ 2](results/2.md) | [Критерии](results/2.grading.json) |
| 3. Спор о достижении | 74/75, срок в будущем, недостаток evidence, запрет подмены критерия | [Ответ 3](results/3.md) | [Критерии](results/3.grading.json) |
| 4. Спорные правила | 14%, 25%, 5★, файлы, маленькая операционная команда | [Ответ 4](results/4.md) | [Критерии](results/4.grading.json) |

Тексты запросов и ожидания — в [evals.json](evals.json).
Полные ответы сохранены; абсолютные локальные ссылки заменены относительными.
Итог первого прогона: **19 из 19 критериев пройдены**. Замечания к полноте
самих критериев сохранены в файлах оценок и не скрываются за итоговым числом.

## Что изменил скилл

[Ответ без скилла](results/baseline.md) дал полезную общую систему: отделил
обязанности от результатов и не придумал базы. Но он предложил 1–3 личных
результата на квартал и допустил частичное достижение. Это не ошибки общего
консалтинга; это расхождения с конкретной реконструированной методикой.

Ответ со скиллом сохранил 2S/2M/1L, самостоятельный выбор сотрудника,
непрерывную постановку, оценку амбиции и бинарный финальный результат.
В сценарии спора он различил недостижение к истёкшему сроку и цель,
по которой эффект пока не подтверждён.

## Автоматические проверки

```bash
python -m unittest discover -s tests -v
python tools/check_release.py
python tools/package_skill.py
python skills/company-goal-system/scripts/audit_goals.py examples/orion-goals.csv --json
```

Тесты покрывают календарные границы, лимиты портфеля, статусы, структуру CSV,
длину формулировок, повреждённые данные, безопасную установку и упаковку.
Установка проверяется во временных проектах, а не в рабочих настройках пользователя.
Два теста символьных ссылок могут пропускаться на Windows без права их создания.
В GitHub Actions предусмотрены Linux и Windows, Python 3.10 и 3.13.

Структурный валидатор skill-conductor проверил 11 правил: все пройдены,
без предупреждений. Он оценивает структуру файла, а не результативность методики.

## Границы проверки

- Шесть запросов в [triggers.json](triggers.json) проверяют выбор по описанию.
  Это отдельные решения чистых агентов, не измерение автоматического обнаружения
  навыка внутри установленных Claude Code и Codex. Итог: **6 из 6 совпадений**
  с ожидаемым выбором; [ответы проверяющих](results/routing.json).
- Четыре поведенческих сценария не доказывают качество на всех запросах.
  Особенно полезно дополнить их случаями сложной матричной организации.
- Большой ответ при запуске нужно оценить с реальными участниками: он подробный,
  но для короткой встречи может потребоваться выдача по этапам.
- Программный аудитор не проверяет смысл цели, согласие сотрудника,
  подлинность evidence, экономический эффект или справедливость оценки.
- Проверка чувствительных данных по шаблонам дополняет ручной просмотр;
  она не гарантирует автоматическую анонимизацию любых будущих изменений.
- Время, токены, стоимость и экономический эффект не измерялись.

При изменении методики сначала обновите ожидания с объяснением причины,
затем сохраните новый ответ и его оценку. Не меняйте критерии лишь ради
успешного прохождения текущего ответа.
